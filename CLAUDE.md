# רק רגע לקרוא — Project Context

This file exists to preserve architectural decisions and their reasoning across sessions — update it when a decision here changes, not just when code changes.

## Product overview

My Reading Moment is a Hebrew reading-practice application for children aged 6–10.

The child reads a short passage and answers a free-text comprehension question. Answers may contain reasonable spelling mistakes, so correctness is evaluated semantically rather than through exact string comparison — implemented for real via the Gemini provider's `evaluateAnswer` (see "LLM provider architecture" below). The mock provider still uses deterministic normalized-text matching instead, as a lighter stand-in for development and tests (see "Mock `evaluateAnswer` is deterministic, not semantic" below).

If the answer is not accepted, the child receives supportive feedback and may request a different question about the same passage and at the same reading level.

A possible future direction is expanding the flow to approximately three questions from different angles per passage — not implemented now.

`client/` is Vite + React + styled-components; `server/` is Express, ES modules (`"type": "module"`).

  - The 3-questions-per-text feature is not built. `TextResult.evidence` (`{questionsTotal, questionsCorrect}`) and the "success" determination in `textCompletionRules.js` are shaped to generalize to more than one question without a rework, but the actual multi-question generation/UI doesn't exist yet.
  - No UI reads `currentLevel`/`currentSublevel` or reacts to a Progression-driven sublevel change (e.g. a bigger visual "world" transition on a level-up) — a deliberately deferred UX idea, not to be built until asked for.
  - Mock provider content is only hand-authored at levels 1.1 and 2.2; other rungs are synthesized deterministically so local/dev/test progression can still exercise all 16 combinations.

Deliberately deferred as a UI/UX pass, not done as part of the server-side fix.
- **Completed sessions have no memory cleanup/TTL.** `readingSessionStore`'s `sessions` Map only ever grows — a session past `"completed"` is removed from `activeSessionIdByChildKey` (freeing the child for a new one) but the completed session object itself is never deleted from `sessions`, so it stays in memory for the life of the process. Not a problem yet at current scale, but a real unbounded-growth issue for a long-running process — a future task, not addressed now.

## Grammatical-gender rule

`grammaticalGender` must come only from the selected child profile. Supported values:

```js
"female"
"male"
```

There is no default grammatical gender. Missing or unsupported grammatical gender is a **data-contract failure** — do not guess, silently fall back, or hardcode a gender in the client.

`grammaticalGender` is validated server-side in `/preview` (`isValidGrammaticalGender`, `readingSessionRoutes.js`) and returned in the response; an invalid/missing value on the child profile is treated as an internal data-contract failure and returns the same stable preview-failure response as any other `/preview` error — never a partial response, never which field was invalid.

## Core architectural decisions (and why)

**The reading session is the source of truth, not `mockPassages`.** `server/src/services/readingSessionStore.js` stores a *snapshot* of the passage (`{id, title, text, level, sublevel}` — no `questions` array) plus the exact `currentQuestion` and `askedQuestionIds` at session-creation time. `/answers` and `/next-question` read from the session, never re-look-up `mockPassages`. Why: a real LLM-generated question won't exist in any static seed list, and the passage text itself could differ per generation — the session must be self-contained.

**`expectedMeaning` never crosses HTTP.** The provider's `generateQuestion` returns it (server needs it later for `evaluateAnswer`), but every route response is built through an explicit whitelist (`toSafeQuestion`) — never a raw pass-through.

**Evaluation contract is data, not presentation.** `evaluateAnswer` returns exactly `{ questionId, isCorrect, feedbackType: "correct"|"retry" }` — no message, no tone/color. The client picks child-facing wording itself. This keeps the LLM boundary purely semantic.

**`"exhausted"` is a mock artifact, not a product state.** The current mock has a finite seeded question list per passage and can run out; a real LLM wouldn't. It's handled as a graceful fallback (`{question: null}` from `/next-question`), explicitly *not* one of the UI's named states. Session/question-count limits (a real product concept) will be designed separately later — don't conflate the two.

**Provider contract is intentionally minimal and mock-agnostic.** `generateQuestion({passage, askedQuestionIds})` only requires `passage.id/text/level/sublevel` (what a real generator actually needs) — the mock's own lookup into `mockPassages` by `id` is an internal implementation detail, asserted nowhere in the shared contract tests (`server/tests/support/llmProviderContract.js`). That shared suite now runs, unchanged, against both `mockProvider.js` and `geminiProvider.js` (see `server/tests/providers/mockProvider.test.js`/`server/tests/providers/geminiProvider.test.js`) — the re-runnability held up in practice, not just in theory. Routes never branch on mock-vs-real — proven by tests that stub the provider module and check the route only forwards its output.

**Session store stays minimal on purpose.** `createSession`, `getSession`, `replaceCurrentQuestion`, `recordIncorrectAttempt`, `tryClaimSession`/`releaseSession`/`completeSession` (the claim/release/complete state machine — see "Learning model" below), `hasActiveSessionForChild`/`getActiveSessionForChild`, and a test-only `clearSessions` — each added because a specific flow needed exactly that mutation. No generic `updateSession(id, patch)` — that would permit arbitrary mutations before the retry/next-question transition rules are even defined. Add focused, named mutations only, as new flows need them.

**Routes validate before mutating.** E.g. `/next-question` validates the provider's returned question (non-blank `id`/`prompt`/`expectedMeaning`, matching `passageId`, not already in `askedQuestionIds`) *before* calling `replaceCurrentQuestion` — a malformed provider result must never leave the session half-mutated.

**Answer-cycle flow:**
```
answering → checking → correct                (checkpoint, NOT session completion —
                                                 a later step may add an animation + stage
                                                 transition here; don't treat it as terminal)
answering → checking → retry → [user clicks "another question"] → generating → answering
any request failure → error
```
`retry` is a real waiting state with an explicit user action — the client does *not* auto-fetch the next question.

**Passage selection is by `level`/`sublevel` (the Reading Level Spec), not the legacy `readingLevel` enum.** `/preview` calls `generatePassage({level: child.learningProfile.currentLevel, sublevel: child.learningProfile.currentSublevel, interests})` — never by array position, interests, name, or id. If no passage matches, it returns the same stable preview-failure response as any other `/preview` failure, and never calls `generateQuestion` or `createSession` (see `readingSessionRoutes.js`). The mock provider requires an **exact** level/sublevel match (see "Reading Level Spec" below) rather than a nearest-neighbor fallback — a session's recorded level/sublevel must never silently differ from what was actually served.

**Mock `evaluateAnswer` is deterministic, not semantic.** The mock normalizes (trim, lowercase, strip common punctuation, collapse whitespace) both `answerText` and the session's own `question.expectedMeaning`, then checks whether the normalized expected meaning contains the normalized answer (minimum 2 normalized characters, to reject trivial single-letter matches). This lets the current build be exercised manually without a real LLM — it is explicitly *not* the future semantic evaluator, and it never trusts an `expectedMeaning` sent by the client (that field is server-only and never crosses HTTP, per the `expectedMeaning` decision above).

**Active-child identity lives in `ActiveChildProvider`, not the URL.** `/children` (child selection) and `/child-home` (temporary destination) both read/write `activeChildId` through `client/src/context/useActiveChild.js`. The backing `ActiveChildProvider` is mounted once in `App.jsx`, inside `BrowserRouter` but wrapping `Routes`, so the same instance persists across navigation instead of remounting per route. The id is only ever a value in memory — it's never put in the URL and never rendered in the UI, and it does not survive a reload. (`activeChildContext.js`/`ActiveChildProvider.jsx`/`useActiveChild.js` are three separate files, not one, because a file mixing a component export with a hook export trips the `react-refresh/only-export-components` lint rule — don't recombine them.)

**`/child-home` is now the real first version of the child's personal-world screen.** Selecting a profile on `/children` calls `selectActiveChild(profile.id)` then navigates to `/child-home`, which resolves and renders that child's own screen (see "Active profile resolution" above) — it's no longer a bare placeholder. If `/child-home` is reached with no active child set (a direct visit or a reload, since the provider holds no persisted state), it redirects back to `/children` via `<Navigate replace>` rather than rendering anything.

**Avatar rendering is centralized in one function.** `client/src/constants/childAvatars.jsx` exports `getChildAvatar(childProfile)` — the single source every avatar-consuming component calls. It currently always returns the same placeholder icon regardless of the profile, but returns a ready-to-render node rather than a component reference, so a real per-child avatar (image, SVG, URL) later only changes this function's body, not `AvatarButton` or any call site.

**Active profile resolution reuses the existing profile list, not a new endpoint.** `ChildHomePage` resolves the active child by calling the same `fetchChildProfiles()` `ChildSelectionPage` already uses, then finding the profile whose `id` matches `activeChildId`, client-side. No `GET /api/child-profiles/:id` was added — the dataset is small and already fully fetched elsewhere, so a dedicated endpoint now would be premature. An `activeChildId` that matches no fetched profile (stale/unknown id) is treated exactly like "no active child" — redirect to `/children` — rather than a separate error state.

**`ActiveChildProvider` accepts an optional `initialActiveChildId`, for tests only.** It seeds the very first render, the same way `MemoryRouter`'s `initialEntries` do — it is not a controlled prop, `selectActiveChild` is still the only way to change the value after mount, and `App.jsx` never passes it, so production behavior is unchanged. This exists because seeding the context from a wrapping test component's effect races with `ChildHomePage`'s own `<Navigate>` effect, and mutating a different component's state during another component's render is unsafe.

**Stations are numbered, not iconified, and carry no visible caption.** `StationNode` shows a plain step number inside each circle instead of an icon or a caption underneath, whether `completed`, `active`, or `locked` (see "`StationNode` has three statuses..." below for the third). The active station relies on the page's own greeting heading to state the action; completed/locked stations need no visible caption, since the circle's color plus the accessible label already communicate the state. Accessibility is carried entirely by composed `aria-label`s instead: the active station's button gets one (e.g. "שלב 1, התחלת תרגול קריאה"); each non-interactive station is a `role="group"` with its own (e.g. "שלב 2, נעול" / "שלב 1, הושלם") — built from the shared `stepLabelPrefix`/`lockedStepStatusLabel`/`completedStepStatusLabel` text keys.

**`AvatarDisplay` vs `AvatarButton`: a passive display and a clickable control are different components.** `ChildHomePage` shows the active child's avatar via `AvatarDisplay` (a plain, non-interactive wrapper), not `AvatarButton` (a real `<button>`) — reusing a clickable button for something that does nothing on click would be the wrong semantics. Both share the same `AvatarCircle`/`AvatarLabel` styles from `AvatarButtonStyle.js`.

**The reading-practice bridge from `/child-home` is no longer temporary.** The active station still calls `navigate('/')`, but `ReadingSessionPage` now reads `activeChildId` directly instead of showing its own child-selection dropdown (see "`ReadingSessionPage` now uses the active child directly..." below) — the flow is a path to practice, not a return to a form. `/` still doesn't encode *which* station was clicked (there's only one kind of practice content today); that would matter if per-station distinct content is ever needed.

**The child's name and the welcome heading stay two separate elements.** `ChildHomePage` shows the name via `AvatarDisplay` (raw profile data, same as `ChildSelectionPage` already does) and a fully self-contained, gendered heading via `resolveText('childHome.heading', ...)` — never one sentence with the name interpolated into it. This avoids adding string-interpolation support to `resolveText`/`text.js`, which today only resolves plain strings or `{female,male}` variants.

**`ChildHomeGreeting` is a semantic `<h1>`, styled to look the same as before.** It was originally a styled `<p>`; `font-weight: normal` is set explicitly to counteract the browser's default bold heading weight, so only the semantic tag changed, not the visual design.

**`ReadingSessionPage` now uses the active child directly, with no dropdown or profile fetch of its own.** It reads `activeChildId` from `useActiveChild()` and redirects to `/children` (via `<Navigate replace>`, same pattern as `ChildHomePage`) if it's missing. `fetchChildProfiles` is no longer called here at all — `grammaticalGender` already comes back in the `/preview` response, so nothing needed the profile list.

**`fetchReadingExercise` (`/preview`) is deduplicated per mount, not just per response.** A plain `ignore` flag (the standard fetch-in-effect pattern used elsewhere) only discards a *stale response* — it does not stop a stale *request* from being sent, and `/preview` is not idempotent (it creates a server-side session). `ReadingSessionPage` caches the in-flight/settled request in a ref keyed by `activeChildId`, so `fetchReadingExercise` is only ever called once per child under React StrictMode's double-invoked mount effect — each effect instance still attaches its own `ignore`-gated handler to the shared promise. Without this, StrictMode's dev-only double mount would silently create an orphan session per page load.

**Learning-path progress is persisted server-side, keyed by child, not client-only.** `ChildHomePage` reads `journeyProgress` straight from the fetched child profile on every mount. The former `LearningPathProvider`/`useLearningPath`/`learningPathContext` (a three-file split mirroring `ActiveChildProvider`, same `react-refresh/only-export-components` reason) have been removed entirely — a client-only copy of the same number was a source of drift, not a real need, once a real parent/child account existed to persist it against. See "Learning model: Active Session, TextResult, Progression, Journey Progress" below for the full current model — `journeyProgress` used to be called `completedStepCount` and used to live inside `learningProfile`; both changed once Learning Progression (a genuinely separate, pedagogical concept) was introduced.

**Every evaluated answer is recorded server-side, correct or not — and recording it is required, not best-effort.** `/answers` (`readingSessionRoutes.js`) appends an `answer_attempt` learningEvent (`{questionId, isCorrect}`, plus `source: "system"` and a timestamp) to the child's `learningEvents` array via `parentRepository.addLearningEvent` — recorded from the server's own evaluation result, never trusting the client to report its own outcome. `addLearningEvent` is `await`ed *before* the response is sent, and its failure falls through to the same `catch` (and the same generic `500`) as a failed `evaluateAnswer` call. This is a deliberate correction from an earlier best-effort/fire-after-response version: the learning history isn't a debug aid or a nice-to-have side effect — it's the core product record this whole app exists to build over time (how the child reads, what they struggle with, how practice should adapt), so a child is never told "correct"/"try again" for an answer that didn't actually get recorded.

**Station status (`completed`/`active`/`locked`) is derived, not stored.** `ChildHomePage` computes `currentActiveStep = journeyProgress + 1` and classifies each rendered station from that one number (`< currentActiveStep` → completed, `===` → active, `>` → locked) — there is no separately-stored "which step is active" field. This makes "exactly one active station" an invariant of the arithmetic rather than something that could desync across two fields. The number of *rendered* stations is `currentActiveStep + STATIONS_LOOKAHEAD` (a small constant buffer of upcoming locked stations, currently 3) — there is deliberately no fixed total; see "Journey Progress has no maximum" below.

**Only a correct answer ever advances progress, and it now happens automatically, server-side.** The server determines a text's outcome inside `/answers` (see "Learning model" below) — `journeyProgress` and Learning Progression update in the same request that evaluates the terminal answer, not via a separate client-triggered call. `ReadingSessionPage`'s `handleReturnToPath()` now only navigates to `/child-home`; it no longer calls any progress-advancing endpoint (the former `completeLearningPathStep`/`POST /api/child-profiles/:childId/complete-step` were removed — they would have double-counted `journeyProgress` against the new automatic server-side increment). `hasReturnedToPathRef` still guards against a double-click firing `navigate()` twice, since `navigate()` doesn't unmount the component synchronously — that guard is now purely about navigation, not about a data write.

**After 3 incorrect attempts, the child returns to the path without advancing progress — no further retry loop.** `MAX_INCORRECT_ATTEMPTS = 3` is defined **only server-side** (`textCompletionRules.js`) — the server tracks `incorrectAttemptCount` on the active session itself (`readingSessionStore.js`) and independently determines when a text has failed. The client's `ReadingSessionPage` no longer counts attempts or knows the limit at all; it renders `correct`/`retry`/`attemptLimitReached` purely from the `textOutcome` field `/answers` returns (see "Learning model" below) — an earlier version duplicated `MAX_INCORRECT_ATTEMPTS` client-side and inferred the limit locally, which a review flagged as a real divergence risk (a double-submit could advance the server's count without the client knowing). The message shown is a single gentle, gender-neutral string (not a `{female,male}` variant, since it avoids conjugated verbs) that never uses "wrong" or "failed" language — the child is not told this was tracked as anything. Per-answer history is recorded server-side (see "Every evaluated answer is recorded server-side" above) and now **is** read back — see "Learning model" below for how a failed text feeds into Learning Progression.

**`StationNode` has three statuses, not two.** `completed` reuses the same numbered-circle pattern as `active`/`locked` (per "Stations are numbered, not iconified" above) — only the circle's color changes (`theme.colors.success`), keeping that established convention instead of introducing icons. Like `locked`, it renders as a non-interactive `role="group"` (composed accessible label via `stepLabelPrefix`/`completedStepStatusLabel`), since there's no distinct per-station content to revisit yet.

## Authentication & ownership

Parent accounts are real (MongoDB-backed via `parentRepository.js`), not mocked — registration/login issue a JWT stored in an httpOnly cookie (`tokenService.js`: `generateToken`/`verifyToken`, `AUTH_COOKIE_NAME`), never returned in a response body, so it can't end up in browser history, logs, or client-side JS.

**`requireAuth` is deliberately stateless.** `authMiddleware.js` only verifies the token and attaches `req.parentId` — it never touches the database. Loading the actual parent document is the route's job (via `parentRepository`), keeping "who is this" (middleware) separate from "what do they have" (route). A missing, expired, malformed, or mis-signed token all produce the same generic 401 — callers must never be able to distinguish which.

**Every child lookup is ownership-scoped, never a bare id lookup.** `parentRepository.updateChild`/`applyTextCompletionProgress`/`addLearningEvent` all filter by the compound `{ _id: parentId, "children._id": childId }` — a childId belonging to another parent is indistinguishable from one that doesn't exist at all (same 404, same error shape). `/preview` (`readingSessionRoutes.js`) applies the same principle by loading the parent via `req.parentId` first and looking up the child as a subdocument, never by querying children directly. `TextResult` (a separate top-level collection, not embedded — see "Learning model" below) follows the same discipline: every query filters by `{parentId, childId, ...}`, never `childId` alone, even though `childId` (a Mongo ObjectId) is already technically globally unique — the extra field is about consistency with this ownership convention, not query correctness.

`POST /api/reading-sessions/preview` and all of `/api/child-profiles/*` require `requireAuth`. `/answers`, `/next-question`, and `/skip` don't — they operate purely on an opaque `sessionId` that was already tied to a `parentId`/`childId` at session-creation time (see "Learning model" below), not on anything the caller could forge ownership of.

## Learning model: Active Session, TextResult, Progression, Journey Progress

The product's whole point is adaptive reading practice over time, not a static practice screen — this section is the data model that makes that real. Four concepts, each with a distinct, non-overlapping responsibility:

**Active Reading Session** (`readingSessionStore.js`) — unchanged in spirit (temporary, in-memory, resets on server restart — see "reading session is the source of truth" above), but now also holds everything needed to determine when a text is *finished*, not just what's being read:
- `level`/`sublevel` (numbers) — the child's pedagogical position **at the moment the text was generated**, captured once from `child.learningProfile.currentLevel/currentSublevel` and never re-read from the live profile afterward. This is deliberate: a `TextResult` must reflect what the text actually was, even if the child's profile changes mid-session.
- `incorrectAttemptCount` — server-owned now (see the attempt-limit note above); a new `readingSessionStore.recordIncorrectAttempt(sessionId)` mutation increments it.
- `state: "active" | "locked" | "completed"` — see "the session claim" below.
- `startedAt` — captured at session creation, carried onto the eventual `TextResult`.

**One active session per `parentId`+`childId` — and `/preview` resumes it rather than dead-ending.** A second in-memory index (`activeSessionIdByChildKey`, keyed by the pair, not `childId` alone — same ownership discipline as everywhere else) lets `readingSessionStore.createSession` refuse (return `null`) a second session for a child that already has one. Different children of the same parent never conflict with each other. **This invariant is guaranteed only within a single Node process** — `readingSessionStore` is an in-memory `Map`, not backed by Mongo/Redis, so it is not shared across instances. Running more than one server process/container today would let two `/preview` requests for the same child, routed to different processes, each create their own "only" active session. Nothing in this codebase enforces single-process deployment; it is a known, currently-unaddressed assumption. If this ever needs to run as more than one instance, active-session ownership (the claim, the state machine, the one-per-child index) would need to move to a shared store keyed by `parentId`+`childId`, not stay process-local. `/preview` checks `getActiveSessionForChild` **before** calling the (costly) LLM provider, and again after a `createSession` race-loss (closing a narrow race where two concurrent `/preview` requests both pass the first check) — either path returns the **existing** session's exercise data (same shape `/preview` always returns, `200`), not a fresh one, and **never silently cancels it**. This is a review-driven fix: an earlier version returned `409` here, which meant a refreshed tab, a lost connection, or simply navigating away and back left that child permanently unable to start or resume practice until the whole server restarted — the in-memory store has no expiry. `/skip` remains the way to deliberately abandon a session and free the child up for a genuinely new one. The index entry is freed only when the session reaches `completed`.

**`/preview` only ever resumes a session whose state is `"active"` — a `"locked"` session gets a deterministic `409`, never its stale snapshot.** A second review finding on the resume behavior above: `getActiveSessionForChild` (deliberately, see its own tests) finds a `"locked"` session too, since other callers need that — but `/preview` resuming one is a distinct bug. A session is `"locked"` while another mutating request (typically `/next-question`) is awaiting the provider; if `/preview` handed back that in-flight session's *current* `currentQuestion`/`sessionId` snapshot, a client that refreshed mid-mutation would be shown a question the server is about to replace, and a subsequent `/answers` call would be evaluated against the wrong question. `/preview` (both the main resume check and the narrow post-`createSession`-race branch, `readingSessionRoutes.js`) now checks `existingSession.state === "active"` before resuming, and returns `409` otherwise — without cancelling the existing session or creating a new one. The child can simply retry in a moment once the in-flight mutation finishes and releases the session back to `"active"`.

**The session claim (`sessionClaim.js`'s `withClaimedSession`) protects *every* mutating request on a session, not just the terminal one.** An earlier version of this only guarded the finalize step, on the assumption that evaluating an answer was side-effect-free and safe to repeat — an external review caught that this was wrong: a losing concurrent request could still write a `LearningEvent` and return its own (possibly different, especially with non-deterministic Gemini output) evaluation, contradicting whatever the winner actually recorded as the canonical `TextResult`; and a non-terminal wrong answer had no protection at all, so a double-submit could double-count an attempt. The fix generalizes the lock: `readingSessionStore.tryClaimSession(sessionId)` is a **synchronous** compare-and-swap (`active` → `locked`) — synchronous specifically so it can't be raced by a concurrent request arriving during an `await` (Node is single-threaded, but `await` points do yield to other requests; a same-tick synchronous check-and-set is safe where a plain `completed: boolean` read-then-write across `await`-separated steps would not be). It returns `{ok: false, reason: "not_found" | "conflict"}` so callers can return 404 vs 409 — **every** mutation (`/answers`, `/skip`, `/next-question`) now claims first, and a losing request is rejected immediately, before evaluation, DB writes, or the LLM are ever touched — not silently repeated. `withClaimedSession(sessionId, work)` wraps the claim: `work` decides whether to call `readingSessionStore.completeSession` (terminal) or just return (non-terminal, auto-released back to `active`); on `work` throwing, it's released back to `active` too, so a legitimate retry isn't permanently locked out.

**TextResult** (`models/TextResult.js`, `repositories/textResultRepository.js`) — a separate, **top-level Mongo collection** (not embedded under `Parent`, unlike everything else in this app), because its whole purpose is a query pattern (`parentId, childId, level, sublevel, completedAt` — "the last N results for this child at this sublevel") that a real index serves well and an embedded array doesn't. Fields: `{sessionId, parentId, childId, level, sublevel, specVersion, result: "success"|"failure"|"skipped", startedAt, completedAt, evidence}` — deliberately **not** the passage text, question text, or the child's typed answer (over-persistence with no current use case; `evidence` is a minimal aggregate like `{questionsTotal, questionsCorrect}`). `specVersion` (`READING_LEVEL_SPEC_VERSION`, `readingLevelSpec.js`) is stamped so historical results stay interpretable if the spec's difficulty definitions ever change. TextResult is the **canonical, durable outcome of a completed text** — the source of truth Progression reads, never re-derived from `LearningEvent` (which stays exactly what it already was: a raw, granular, per-answer log — the two serve different purposes and are written independently, from the same in-memory data, not one from a DB read of the other).

`sessionId` carries a **unique index** — a durable backstop independent of `readingSessionStore`'s in-memory claim, which only protects a single process. It guards against a retry after an ambiguous transaction outcome, a mid-finalization process restart, or (later) more than one server process — cases the in-memory state machine alone can't see.

**A duplicate-key hit on that index is treated as an idempotent replay, not a fatal completion failure.** `mongoose`'s `session.withTransaction` silently retries its entire callback on a transient/ambiguous commit error — meaning a transaction that actually committed on an earlier attempt can re-run `textCompletionService.js`'s `completeText` and hit the unique `sessionId` index on the second attempt's `TextResult` insert. Treating that as an ordinary error was a review-flagged bug: the route's `withClaimedSession` would release the session back to `"active"` even though the completion had already durably committed, leaving the child permanently unable to progress past that text (every retry re-hits the same duplicate key). `completeText` now catches specifically that error (`error.code === 11000`) around the whole `withTransaction` call (not inside it — a Mongo transaction aborts entirely the instant any operation inside it errors, so the failed attempt's session is already dead by the time the error surfaces; recovery has to run a plain, non-transactional read via `textResultRepository.findBySessionId`, not try to reuse it), and returns the existing `TextResult`'s canonical `result` with `alreadyCompleted: true` — making **no further writes at all** (no second `LearningEvent`, no double `journeyProgress`/Progression update) regardless of whether the attempted `result` matches what's already recorded. A mismatch (the retry attempted a different outcome than what's canonically stored) is deliberately *not* surfaced as a distinct conflict type — the already-committed result is definitionally the truth, and neither route currently inspects `completeText`'s return value beyond letting it not throw, so there's nothing more for a caller to react to today.

**Server-determined, not client-triggered.** `/answers` (`readingSessionRoutes.js`) computes the outcome itself, via `textCompletionRules.js`'s `determineAnswerOutcome({isCorrect, incorrectAttemptCount})` — `isCorrect: true` is always terminal (`"success"`); an incorrect answer is terminal only once `incorrectAttemptCount >= MAX_INCORRECT_ATTEMPTS`. The response also carries `textOutcome: "continues" | "success" | "failure"` — the client (`ReadingSessionPage.jsx`) renders its `correct`/`retry`/`attemptLimitReached` state from this field directly; it no longer counts attempts or knows `MAX_INCORRECT_ATTEMPTS` itself (an earlier version duplicated the constant client-side, which a review flagged as a real divergence risk under retries). A new `POST /api/reading-sessions/skip` (no auth — same opaque-`sessionId` pattern as `/answers`/`/next-question`) lets a child explicitly abandon a text; it always finalizes with `result: "skipped"`. Abandoning a session any other way (closing the tab, a lost connection, a server restart) does **not** produce a `TextResult` — by construction, since `TextResult` is only ever written inside a real `/answers` or `/skip` request.

**The completing write is one real Mongo transaction** (`textCompletionService.js`'s `completeText`), not a best-effort sequence: insert the new `TextResult`, then (still inside the transaction) the terminal `answer_attempt` `LearningEvent` if there is one (`/skip` has none — `parentRepository.addLearningEvent` now accepts `{session}`), then (in the **same** `mongoose.startSession()`/`withTransaction`) read `textResultRepository.findRecentRaw`/`findRecentNonSkipped` — which therefore *includes* the just-inserted result — compute Progression, and `parentRepository.applyTextCompletionProgress` (one `findOneAndUpdate`: `$inc` on `journeyProgress` iff `result === "success"`, `$set` on `currentLevel`/`currentSublevel` iff Progression changed them). All of it commits together or not at all — there is no window where a `LearningEvent`/`TextResult` is saved but the child's derived state isn't, or vice versa (an earlier version wrote the `LearningEvent` *before* the transaction, so a transaction failure could leave a learning-history record with no matching `TextResult` — also caught by review). This is why `server/tests/support/globalSetup.js` uses `MongoMemoryReplSet` (not a standalone `MongoMemoryServer`) for tests — transactions require a replica set, and Atlas (production) already is one, so this only affects local test infra. **A write made without passing `{session}` through every call silently runs outside the transaction** — a real pitfall, covered explicitly by `tests/support/transactions.test.js`.

**`completeText` throws (aborting and rolling back the whole transaction, `TextResult` included) if `addLearningEvent`/`applyTextCompletionProgress` report that the child no longer exists.** Neither the parent nor child deletion is reachable through any route today, but the contract must hold regardless — nothing today rules out a future delete feature or a manual data-repair scenario landing between an active session's creation and its completion. This required fixing a real ambiguity first: `applyTextCompletionProgress` returned `null` both for "no such child" *and* for "child exists, nothing to `$inc`/`$set`" (an ordinary, frequent case — e.g. an outcome that doesn't cross a Progression threshold) — the same value meaning two different things. It now does an explicit existence check when there's nothing to mutate, so `null` unambiguously means "not found" in every path, and `completeText` can safely treat it as fatal without misfiring on the common no-op case.

**Learning Progression** (`progression.js`, pure function, no I/O — `computeProgression({level, sublevel, recentRaw, recentNonSkipped})`) implements exactly three rules, in this priority (provably non-conflicting in practice — see below):
1. The 2 most recent results (raw, **unfiltered** — `recentRaw`) are both `"skipped"` → sublevel decreases.
2. Among the last 4 results that are **not** `"skipped"` (`recentNonSkipped` — skips are filtered out in the *query itself*, `{result: {$in: ["success", "failure"]}}`, so a skip never occupies a slot in this window) — at least 3 `"success"` → sublevel increases.
3. Among the last 3 of that same non-skipped list — at least 2 `"failure"` → sublevel decreases.

`TextResult` carries **two** compound indexes with the identical key pattern `{parentId, childId, level, sublevel, completedAt}` (explicitly named `recent_raw` and `recent_non_skipped` — Mongo requires distinct names when the key pattern collides) — the second is a **partial index**, `partialFilterExpression: {result: {$in: ["success", "failure"]}}`, matching `findRecentNonSkipped`'s query exactly so Mongo excludes `"skipped"` rows via the index itself rather than walking past them while scanning.

A skip is intentionally invisible to rules 2/3 — it's a separate signal channel (not evidence of reading ability by itself), only meaningful as a *pair*. Sublevel changes cross level boundaries (1.4 up → 2.1, 2.1 down → 1.4) via `nextRung`/`previousRung`; below 1.1 or above 4.4 the result **clamps** (`changed: false`) rather than erroring. Rule priority never actually matters in practice: a `"skipped"` TextResult can only ever trigger rule 1 (it's filtered out of rules 2/3's windows entirely), and a `"success"`/`"failure"` TextResult immediately breaks any skip streak (rule 1 needs the *most recent* entry to be a skip) — so a single new TextResult can only ever be capable of triggering the rule matching its own type.

**Reading Level Spec** (`data/readingLevelSpec.js`) — the structured, machine-readable definition of all 16 level/sublevel combinations (`level` 1–4 × `sublevel` 1–4), replacing the old flat 3-value `readingLevel` enum ("beginner"/"intermediate"/"advanced") as what actually drives generation. Each entry: `{level, sublevel, nikud, textLengthSentences: {min,max}, wordsPerSentence: {min,max}, vocabularyAndMorphology, syntax, comprehensionTarget}` — numbers where the axis is a range, short structured strings for nikud (a fixed vocabulary like `"full"`/`"mixed"`/`"none"`), free Hebrew prose only for the genuinely qualitative axes. `getReadingLevelSpec(level, sublevel)` throws for anything outside 1–4 — there is no fallback. `prompts.js`'s `buildPassagePrompt`/`buildQuestionPrompt` are the sole consumers, translating each axis into Hebrew guidance sentences for the LLM — this is why difficulty isn't simply "longer text": level 3 (introducing reduced nikud) deliberately has a *shorter* text-length range than late level 2, trading one axis for another rather than raising every axis at once.

**The legacy `readingLevel` enum still exists on `learningProfile` and is still parent-editable via `PATCH /api/child-profiles/:childId`, but no longer drives generation at all — and no longer sets the child's starting `currentLevel`/`currentSublevel` either** (those always default to `1`/`1` at creation, regardless of the chosen `readingLevel`). This is a deliberate, known, *unresolved* residual inconsistency — collapsing it into one field/deciding the relationship between "parent override" and "system-computed Progression" is a real product decision, not a mechanical rename (see "Planned direction" below). The one thing that *was* fixed (a review-flagged product-confusion risk): the field's label (`childSelection.readingLevelFieldLabel`) now reads "רמת קריאה **התחלתית**" ("**starting** reading level") instead of an unqualified "reading level" — honest that it's a one-time value entered at creation, not a live/current indicator, without implying it does more than it does. The field is still otherwise fully inert; wiring it to actually seed `currentLevel`/`currentSublevel`, or deciding what a later parent override should mean, is intentionally not done here.

**Mock content is synthesized for any level/sublevel, not just the two hand-authored seed passages.** `mockPassages.js` only has content at 1.1 and 2.2 — everywhere else, `mockProvider.js`'s `generatePassage` falls back to `synthesizePassage(level, sublevel)`, a deterministic placeholder sized to that rung's own `textLengthSentences` (via `readingLevelSpec.js`), paired with exactly one `synthesizeQuestion`. This exists because Learning Progression can move a child to *any* of the 16 rungs — without it, three ordinary successes at a seeded rung would walk a child into a sublevel mock mode can't serve at all, breaking `/preview` (a real review finding: local/dev/test flow would die after a few minutes of normal use). Real (Gemini) generation was never affected — it generates fresh content for any level/sublevel already.

**`journeyProgress` (was `completedStepCount`) is a sibling field on the child, not nested inside `learningProfile`.** Deliberately separate from Learning Progression: it advances on every successful `TextResult` *regardless* of whether that same completion also changes `currentLevel`/`currentSublevel` (most successes don't — Progression only moves every 3-of-4 or 2-of-3 window, not every text). `ChildHomePage` reads both independently; a future "world" visual (per station-path milestones) would key off `currentLevel`, while the station-within-the-path position keys off `journeyProgress` — the two signals are independent by design, not just by accident.

**Journey Progress has no maximum.** `ChildHomePage`'s old `TOTAL_STATIONS = 12` is gone — `STATIONS_LOOKAHEAD = 3` is a small **rendering** buffer (always show a few upcoming locked stations past the active one), not a product cap. The station path is meant to be able to grow forever; nothing in the data model (`journeyProgress` is a plain incrementing `Number`, `min: 0`, no `max`) or the rendering logic assumes a final station.

## LLM provider architecture

The provider contract has three functions — `generatePassage({level, sublevel, interests})`, `generateQuestion({passage, askedQuestionIds})`, `evaluateAnswer({passage, question, answerText})` — implemented identically by two providers:

- `mockProvider.js` — deterministic, selects from seeded `mockPassages`/questions by **exact** `level`/`sublevel` match (see "Reading Level Spec" above — the mock's seed data is intentionally small, a lighter dev/test stand-in, not the future semantic generator). Default, and what every automated test runs against.
- `geminiProvider.js` — real generation via the Gemini API. Selected with `LLM_PROVIDER=gemini` (`GEMINI_API_KEY` required, `GEMINI_MODEL` optional).

`server/src/services/llmProvider/index.js` is a selector, resolved once at require-time from `LLM_PROVIDER` (default `"mock"`); it re-exports the chosen provider's own exports object, not a copy, so existing `jest.spyOn` usage keeps working. **Routes stay provider-agnostic** — `readingSessionRoutes.js` only ever calls `llmProvider.*`, never checks or branches on which provider is active.

`geminiClient.js` is the only module that imports `@google/genai` — response schemas, the actual API call, and model selection all live there; `geminiProvider.js` never touches the SDK directly. Prompt construction (including per-`level`/`sublevel` guidance for passage length/vocabulary/nikud and question difficulty, sourced from the Reading Level Spec) lives entirely in `prompts.js`, kept separate so it can be iterated on without touching orchestration or validation logic. Gemini is only ever trusted for prose (title/text, prompt/expectedMeaning, isCorrect) — structural fields (`id`, `level`, `sublevel`, `passageId`) are always assigned by `geminiProvider.js`, never taken from the model's output.

Gemini's `generatePassage`/`generateQuestion` are two independent API calls, not one combined call — `generateQuestion` needs the passage's actual text either way (for both `/preview`'s first question and `/next-question`'s replacements), so a real provider's `generateQuestion` has to work standalone regardless of how `/preview` is wired; reusing it for the first question costs nothing extra. This is the trade-off a combined-call optimization (see "Planned direction" above) would revisit.

## Debug logging

`server/src/services/debugLogger.js` (`writeDebugLog`, `runWithRequestId`) is a temporary perf/debug aid, not the app's logging system — it writes JSON Lines to `server/logs/timing.jsonl`, used by both `geminiClient.js` (timing per Gemini call, tagged `"LLM"`) and `readingSessionRoutes.js` (per-request timing and thrown-error details, tagged `"Route"`/`"Error"`).

- **Opt-in only.** Nothing is written unless `TIMING_LOG_ENABLED=true`; automated tests never write regardless of the flag (`NODE_ENV=test`, set automatically by Jest, is a hard override, not just a default).
- **Best-effort.** The file write is wrapped in `try/catch` — a failure (missing dir, disk error) never breaks the request it's logging; it only prints one short `console.warn`, with the filesystem error's own message but never the log entry itself.
- **`requestId` correlates route and LLM logs automatically**, via `runWithRequestId` (Node's `AsyncLocalStorage`) — a route handler starts it once per request, and every `writeDebugLog` call made anywhere during that request (including deep inside `geminiClient.js`) picks up the same id, with no need to thread it through `generatePassage`/`generateQuestion`/`evaluateAnswer`'s own parameters. Keeping it out of the provider contract is deliberate — request correlation is a debugging concern, not something the contract should know about.
- **Never logged:** prompt text, child answers, generated passage/question/`expectedMeaning` content, or any secret (API keys, etc). Entries carry only metadata — durations, labels, lengths (`textLength`/`promptLength`), `readingLevel`, the Gemini `model` name, and (on error) the error's own name/message/status.

## Docker

A local, production-style build/runtime path exists alongside — not replacing — the npm-based dev workflow (`docker-compose.yml`, `client/Dockerfile`, `client/nginx.conf`, `server/Dockerfile`). Only `client` and `server` are containerized; MongoDB stays external (Atlas), matching existing local dev.

**nginx reverse-proxies `/api` to the server, rather than the client calling the server's exposed port directly.** The client already calls relative `/api/...` paths everywhere (mirroring the existing Vite dev-server proxy) — same-origin from the browser's perspective, which sidesteps `SameSite=Lax` cookie/CORS complications a direct cross-port call would introduce, at the cost of zero client changes.

**nginx resolves the `server` upstream at request time, not at startup.** A bare `proxy_pass http://server:7000` fails nginx's startup entirely if `server` isn't resolvable yet (container start order isn't guaranteed) — `resolver 127.0.0.11 valid=10s;` (Docker's embedded DNS) plus a `set $backend ...; proxy_pass $backend;` indirection defers resolution to request time, so nginx always starts, and unreachable API calls degrade to a `502` instead of nginx never coming up at all.

**The server's port is not published to the host.** `docker-compose.yml` gives `server` no `ports:` — it's reachable only from `client` over the internal Compose network, matching the reverse-proxy decision above (nothing outside the container network is meant to call it directly).

**`NODE_ENV` is deliberately left unset in the server container.** The auth cookie's `secure: NODE_ENV === "production"` flag (`authRoutes.js`) would silently stop the browser from storing the cookie at all over plain HTTP — this Docker setup has no TLS, so setting `NODE_ENV=production` here would break login. This is a known limitation of the current local-only setup, not a decision to revisit lightly.

**`server/.env` is loaded via Compose `env_file`, never copied into the image** (`server/.dockerignore` excludes it) — secrets stay out of the image layers. `CLIENT_ORIGIN` is the one exception: `docker-compose.yml` overrides it to `http://localhost:8080` (the nginx-exposed origin) for the Docker path only, layered on top of whatever `server/.env` has (which keeps `http://localhost:5173` for local `npm run dev`, unmodified).

## CI/CD

`.github/workflows/ci.yml` (tests+lint for both `client`/`server`, plus a client build) and `.github/workflows/cd.yml` are two separate workflow files, deliberately not one job graph.

**CD is triggered by CI's own success, via `workflow_run`, not by re-running tests itself.** `cd.yml` listens for the `CI` workflow (matched by name) completing, and its job `if` explicitly checks all three of `conclusion == 'success'`, `event == 'push'`, and `head_branch == 'main'` — this was a deliberate choice over duplicating the test/lint steps inside `cd.yml`, to avoid running the same checks twice. The three-way check (not just a `branches: [main]` filter on the trigger) is intentional: a bare branch filter alone wouldn't reliably rule out a CI run that was itself triggered by an unmerged PR, which is a real "CD fired when it shouldn't have" risk — checking `event == 'push'` closes that. One consequence of using `workflow_run`: GitHub only picks up a *new* workflow file once it's present on the default branch, so `cd.yml` itself doesn't fire on the push that first adds it — only from the next CI run onward.

**CD builds and pushes Docker images only — it does not deploy anywhere.** There is no hosting target configured yet (no PaaS, no server to SSH into) — see "Docker" above for why the current Docker setup is local-only (no TLS, server port unpublished). `cd.yml` builds `client`/`server` from their existing `Dockerfile`s and pushes to GHCR, using the built-in `GITHUB_TOKEN` (`packages: write`) — no additional secret was needed. It checks out `github.event.workflow_run.head_sha` specifically (the exact commit CI validated), not whatever HEAD of `main` happens to be at trigger time, to avoid a race if another push lands in between. Actually deploying these images somewhere is a separate, not-yet-made decision (see "Planned direction" above).

**Images are tagged by commit SHA only — no `latest`, and the image path is lowercased.** `latest` was deliberately skipped for now (nothing consumes these images yet, so a mutable floating tag has no current consumer to serve and would just be one more thing to reconsider once a real deploy target exists). The image path (`ghcr.io/<owner>/<repo>/<server|client>`) is explicitly lowercased in a dedicated step (bash's `${GITHUB_REPOSITORY,,}`) rather than trusting `github.repository` to already be lowercase — GHCR requires a lowercase path, and repo names/owners aren't guaranteed lowercase in general even though this repo's happen to be today.

## UI text rule

Do not hardcode child-facing UI text inside:

- React components
- event handlers
- conditional branches
- services
- routes

All UI text must be stored under stable semantic keys in the localized text source (`client/src/constants/text.js`).

- Gender-neutral messages remain plain strings.
- Messages that require grammatical-gender variation use explicit variants: `{ female: "...", male: "..." }`.
- New gender-aware UI code must resolve text through `resolveText(key, {language, grammaticalGender})` (`client/src/constants/resolveText.js`), which throws (never falls back) on an unsupported language, missing key, malformed entry, or missing/invalid `grammaticalGender`.
- The transitional `TEXT` compatibility export is only for existing neutral-string consumers and must not be used for new gender-aware text — it actively throws if code touches a gendered key through it (via a getter), so it can never silently leak a `{female,male}` object.
- No i18n library — plain JS objects + one small resolver, deliberately.

## Responsive & typography

- Breakpoints used across `ReadingSessionPageStyle.js` and `styles/components/*Style.js`: `768px` (no rule needed yet — the `480px`-max-width `Card` already fits comfortably), `480px`, `360px`. Each step down reduces `PageShell`/`Card`/`SectionCard` horizontal padding and bumps `Button`/`TextField` padding up slightly for tap-target size.
- `AnswerPanel` (`ReadingSessionPageStyle.js`) is a flex-column, stretch-aligned wrapper — the same pattern `SelectionPanel` already used — so `QuestionStep`'s answer input and buttons stretch to the card's full width instead of shrinking to content width. Reuse this pattern for any new full-width control group; don't invent a second one.
- The reading passage (`StoryText`) uses `line-height: 2.2` specifically for pointed-Hebrew (niqqud) readability — vowel points need more vertical room than plain text. Don't reduce this without checking niqqud rendering again. `theme.js` currently defines only one font (`'Varela Round'`); a different font was deliberately not introduced since the line-height fix was sufficient.

## Component conventions

- `components/ui/*` — fully dumb, reusable, controlled components (`Button`, `TextField`, `SelectField`, `Card`, `PageShell`, `FeedbackMessage`, `AvatarButton`, `AvatarDisplay`, `StationNode`). No app/session knowledge, no text-key resolution, no hardcoded text. Matching styles live in `styles/components/*Style.js`. (`SelectField`/`SelectFieldStyle.js` were removed once, then re-added for the add/edit-child form's gender/reading-level fields — don't remove again without checking every current consumer.)
- `pages/*` — page-level composition (`ReadingSessionPage`, `QuestionStep`, `ChildSelectionPage`, `ChildHomePage`, `LoginPage`, `RegisterPage`) — these *do* know about the domain, own state, and call services, but delegate all HTTP calls to `services/*Service.js`.
- `styles/<PageName>Style.js` — page-specific styled-components (not reused elsewhere).
- `context/*` — application-level state that must survive route navigation (currently just `ActiveChildProvider`/`useActiveChild`), as opposed to page-local `useState`. (`LearningPathProvider`/`useLearningPath` used to live here too — removed once learning-path progress moved server-side; see "Learning-path progress is persisted server-side" above.)

## Testing conventions

- Server: Jest, globals not imported (`describe`/`test`/`expect` are ambient). `server/tests/support/llmProviderContract.js` is a shared, parameterized suite — not a test file itself (no `.test.js` suffix) — invoked by both real and mocked provider test files.
- `server/tests/support/globalSetup.js`/`globalTeardown.js` start **one** shared `MongoMemoryReplSet` (not `MongoMemoryServer`) for the whole test run — a replica set because Mongo transactions require one (see "Learning model" above). Each test file's `testDb.connect()` still gets its own isolated database (a random name on the shared instance), so tests stay fully isolated from each other despite the shared binary.
- Client: Vitest, everything explicitly imported (`describe`/`it`/`expect`/`vi` from `'vitest'`) since `globals: true` isn't set. Always `afterEach(cleanup)` in component tests (state leaks across tests otherwise).
- Every provider-facing route has two test files: one exercising the real mock end-to-end, one mocking the provider module to test error handling and prove the route doesn't branch on mock-vs-real.
- `readingSessionService.js` errors are a structured `ReadingSessionServiceError` (`status`, `body`, `message`) — assert on shape, not just `.toThrow()`.
- **Testing a genuine concurrent-request race (e.g. `readingSessionsSessionLock.test.js`) needs a deterministic signal, not an event-loop-tick guess.** `await new Promise((resolve) => setImmediate(resolve))` to "let the first request get ahead" is not reliable — it caused a real hang during development. Instead, have the mocked dependency (e.g. the provider) itself resolve a promise the moment it's *called*, and `await` that before firing the second request — this proves the first request actually reached that point (which, given the route's own code order, proves it already won the claim) without guessing at timing.
- **supertest's request object is lazy** — `const p = request(app).post(...).send(...)` does not necessarily dispatch the HTTP request until `p` is consumed (`await`ed, `.then()`ed, or `.end()`ed). Holding it in a variable to fire "later" (as when deliberately racing two requests) silently never sends it unless something forces dispatch — chain a `.then()` immediately if the send must happen now but the response should be awaited later.

## Working style for this project

- Work in small, single-concern steps: propose → get explicit go-ahead → implement (including its tests) → run the *full* client and server suites + lint for both → stop for review. Don't bundle unrelated changes into one step.
- When implementing a step surfaces a contract/architecture gap (e.g. a validation missing, two fields that should be one source of truth), stop and propose the fix before continuing — don't silently patch around it.
